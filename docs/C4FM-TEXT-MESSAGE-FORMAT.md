# Yaesu System Fusion (C4FM) text messages: observed format, decoding and generation

**Status:** working, verified on real hardware. The GPS block of GPS-attached messages (5.6) and the position in voice transmissions (5.7) are decoded; sending GPS-attached messages has not been tested.
**Author:** Scot Forshaw (M0RWV).
**Date:** 30 October 2026

## 1. Summary

Yaesu publishes the physical layer and error-coding scheme of C4FM digital voice and data ("System Fusion", Yaesu Musen specification v1.02, July 2015). It does not publish the format of the short text messages that Yaesu handhelds can send and receive.

This document describes that format, as observed from the over-the-air frame payloads that a YSF reflector relays. It covers:

- how a message travels (network packets, frames, coding layers),
- the 200-byte text record that carries a message,
- the checksum, sequence number, timestamp and addressing fields,
- how to decode a captured message and how to build one,
- what is still unknown.

Main findings:

- **Messages are not encrypted or signed.** The text is plain ASCII inside the data channel. Sender and receiver share no key and perform no handshake. A receiver needs only the published frame coding and the record layout below.
- **Integrity** is provided by two checks: the CRC-16 on every coded data unit (published) and a one-byte additive checksum inside the record (found here).
- **Interoperability was tested end to end.** A message generated by software from this description, using only the author's own callsign, was received and displayed correctly (sender, time, text) by a Yaesu handheld that had no part in creating it.

Everything here comes from the author's own radios, the published specification and the author's own reflector. Nothing was taken from firmware, and no protection was bypassed.

## 2. Test setup and scope

- Sending radio: Yaesu FT5D, firmware as shipped, sending text messages to ALL (broadcast) and once to a named callsign, with and without GPS attached to the message.
- Capture point: a YSF reflector on a Raspberry Pi, reading the UDP `YSFD` packets for the author's own callsign only.
- Receiving radio used for the generation test: a second Yaesu handheld with a different radio ID.
- Sample size: eleven transmissions from one radio. Behaviour on other models, other firmware, and other message modes (images, data files, group text) is **not** established.

## 3. Network layer (YSF over UDP)

All values are bytes, strings are ASCII, space padded.

| Packet | Length | Layout |
|---|---|---|
| `YSFD` data | 155 | `"YSFD"` (4) + gateway callsign (10) + source callsign (10) + destination (10) + counter (1) + frame (120) |
| `YSFP` poll/login | 14 | `"YSFP"` (4) + callsign (10). The reflector answers with a `YSFP` packet. |
| `YSFU` unlink | 14 | `"YSFU"` (4) + callsign (10) |

The counter byte is `(frame_index << 1) | end_flag`, with `end_flag` set on the last frame of a transmission. A normal text message without GPS uses counters `0, 2, 4, 6, 8, 10, 13` (frame indices 0 to 6, end flag on the last).

The 120-byte frame is the 960-bit over-the-air frame, MSB first.

## 4. Frame layer

A frame is 960 bits (100 ms):

| Bits | Content |
|---|---|
| 0 to 39 | Frame sync `D4 71 C9 63 4D` |
| 40 to 239 | FICH (frame information channel), 200 coded bits |
| 240 to 959 | Data channel, 720 coded bits |

### 4.1 FICH

32 information bits, protected as follows (all from the published specification):

1. CRC-16 over the 32 bits, appended (48 bits).
2. Four extended Golay (24,12) codewords (96 bits).
3. Four zero tail bits (100 bits).
4. Rate 1/2, constraint length 5 convolution (200 bits).
5. Dibit interleave, 5 dibits wide, 20 deep.

Field order, from the specification: FI (2) CS (2) CM (2) BN (2) BT (2) FN (3) FT (3) Rev (1) Dev (1) MR (3) VoIP (1) DT (2) SQL (1) SC (7).

- FI frame indicator: 0 header, 1 communication, 2 terminator.
- FN frame number, FT frame total minus one.
- DT data type. Text messages used `DT = 1` (data FR mode).
- Only FI, FN, FT and DT were confirmed by this work. The FICH CRC passed on every frame, so the field boundaries are consistent.

### 4.2 Data channel layout in data FR mode (found here)

The 720 data bits are five channels of 144 bits. Each channel holds 72 bits of unit A ("head") followed by 72 bits of unit B ("tail"):

```
unit_A_coded = channel0[0:72] + channel1[0:72] + ... + channel4[0:72]     (360 bits)
unit_B_coded = channel0[72:144] + channel1[72:144] + ... + channel4[72:144] (360 bits)
```

where `channelN` is `bits[240 + 144*N : 240 + 144*(N+1)]`. Each unit carries 20 bytes, so one frame carries 40 bytes of record: unit A, then unit B.

(Reading the two units as consecutive 360-bit blocks does not decode. The interleaved layout above does.)

### 4.3 Data unit coding

Per unit, from the specification and confirmed on real frames:

1. **Whitening:** XOR the 160 data bits with the PN(9,5) sequence. The 9-bit register starts as `S8..S0 = 1 1 1 0 0 1 0 0 1`, the output bit is `S0`, the register shifts towards `S0`, and the new bit entering at `S8` is `S0 XOR S4`. The sequence starts `93 D7 51 21 9C ...`. The register is reset for every unit.
2. **CRC-16:** polynomial `x^16 + x^12 + x^5 + 1`, initial value 0, result inverted, computed **over the whitened bits**, appended MSB first (176 bits).
3. Four zero tail bits (180 bits).
4. **Convolution:** rate 1/2, K = 5, `G1 = 1 + D^3 + D^4`, `G2 = 1 + D + D^2 + D^4` (delays 0,3,4 and 0,1,2,4), output order G1 then G2 per input bit (360 bits).
5. **Interleave:** group into dibits (180), write in rows of 9, read out in columns (9 wide, 20 deep).

Decoding is the reverse: de-interleave, Viterbi decode (hard decision is enough on a clean network copy), drop the tail, check the CRC over the whitened bits, de-whiten.

Reference ordering: the spec text is ambiguous about whether the CRC is computed before or after whitening, and about tap order. Both orderings were tried against real data; only the one above passes the CRC on every captured unit.

Extended Golay (24,12) generator (parity part of `[I | P]`, rows for `d11` to `d0`, columns `p11` to `p0`):

```
110001110101  011000111011  111101101000  011110110100  001111011010  110110011001
011011001101  001101100111  110111000110  101010010111  100100111110  100011101011
```

## 5. The text record

One message is a record of 200 bytes (without GPS), sent as five frames of 40 bytes: frame `FN0` carries bytes 0 to 39, `FN1` carries 40 to 79, and so on.

### 5.1 Frame sequence

| Frame index | Counter | FI | FN | Content |
|---|---|---|---|---|
| 0 | 0 | 0 | 0 | record bytes 0 to 39 (header) |
| 1 to 5 | 2, 4, 6, 8, 10 | 1 | 0 to 4 | record bytes 0 to 199 |
| 6 | 13 | 2 | 0 | record bytes 0 to 39 (terminator) |

FT is 4 for this record length.

### 5.2 Record layout (no GPS, 200 bytes)

| Offset | Length | Content |
|---|---|---|
| 0 | 5 | `*****` |
| 5 | 5 | sender radio ID |
| 10 | 10 | sender callsign |
| 20 | 10 | sender callsign (repeated) |
| 30 | 10 | sender callsign (repeated) |
| 40 | 15 | spaces |
| 55 | 5 | sender radio ID (repeated) |
| 60 | 1 | counter byte: goes up by one for each data transmission the radio sends (text messages and WIRES-X requests, 5.8); it equalled the sequence number minus 16 in the first samples but not later ones |
| 61 | 3 | `Ge_` (no GPS block; `Gf_` when one follows, see 5.6) |
| 64 | 1 | `3` |
| 65 | 5 | sequence number, ASCII digits (the radio's running message count) |
| 70 | 1 | `0` |
| 71 | 10 | timestamp `YYMMDDHHMM`, the radio's local time |
| 81 | 2 | `00` |
| 83 | 10 | timestamp again |
| 93 | 2 | `00` |
| 95 | 5 | destination radio ID (spaces for a broadcast) |
| 100 | 10 | destination callsign (`**********` means everyone) |
| 110 | 80 | message text, space padded, printable ASCII |
| 190 | 1 | `0x03` end of text |
| 191 | 1 | checksum |
| 192 | 8 | `0x00` |

### 5.3 Checksum

```
checksum = sum(record[22:190]) & 0xFF
```

That is the sum of bytes 22 to 189 inclusive, modulo 256, stored at offset 191. It held for all eleven observed records (200 and 240 byte lengths, several texts, broadcast and addressed).

Caveat: every sample used the same callsign and radio ID, so bytes 0 to 40 were constant. Start offset 22 is the only start that fits all samples, but a sender with a different callsign has not been tested against a real receiver (see section 9).

### 5.4 Addressing

- Broadcast (to ALL): destination radio ID blank, destination callsign `**********`.
- Directed to a callsign: destination radio ID is the recipient's 5-character ID, destination callsign is the recipient (observed with a second station's callsign and radio ID). A directed message sent to someone who could not be reached was still decoded correctly from the capture.

### 5.6 GPS-attached messages

With a position attached the marker reads `Gf_`, the record is 240 bytes (six data frames, eight frames in total, FT 5) and a 19-byte block sits at offsets 64 to 82. It starts with the same `3` as in the no-GPS record, so everything after it moves up by 18 bytes: sequence number at 83, timestamps at 89 and 101, destination ID at 113, destination callsign at 118, text at 128 (80 bytes), `0x03` at 208, checksum at 209 (same rule), zeros after.

The block is an **APRS Mic-E** position (APRS 1.0.1 specification, chapter 10):

| Block byte | Content |
|---|---|
| 0 | `3` (constant) |
| 1 to 6 | six latitude digits `DDMMmm`, one per byte: `0x30 + digit` (flag 0) or `0x50 + digit` (flag 1). Trailing digits can be blank for a reduced-resolution position: `L` (flag 0), `K` or `Z` (flag 1). A hotspot user's radio sent `Z` as the last digit, a latitude to 0.1 minute. |
| 7 | longitude degrees + 28 (see below) |
| 8 | longitude minutes + 28 (+60 when the minutes are under 10) |
| 9 | longitude hundredths of a minute + 28 |
| 10 to 12 | speed and course, each + 28 |
| 13 | symbol code `[` |
| 14 | symbol table `/` |
| 15 to 18 | altitude as three base-91 characters then `}`; four spaces when there is none |

Flags in bytes 1 to 6: bytes 1 to 3 are the Mic-E message bits (always 1, 0, 1 here); byte 4 set = north; byte 5 set = longitude offset +100; byte 6 set = west.

Longitude degrees byte: 0 to 9 -> `deg + 118` with the offset flag set; 10 to 99 -> `deg + 28`, flag clear; 100 to 109 -> `deg + 8`, flag set; 110 to 179 -> `deg - 72`, flag set. To decode: `d = byte - 28`, add 100 if the flag is set, then subtract 190 if d >= 190, or 80 if d >= 180.

Speed and course: `SP`, `DC`, `SE` are bytes 10 to 12 minus 28. `speed = SP*10 + DC//10`, minus 800 if >= 800. `course = (DC%10)*100 + SE`, minus 400 if >= 400. The radio sends speed + 800 (0 to 199 knots) and course + 400, so a stationary radio sends `l`, ` `, `0x1c`. With no movement the course value is noise and changes on every message.

Altitude: `((b15-33)*91*91 + (b16-33)*91 + (b17-33)) - 10000` metres. Resolution of the position is 0.01 minute (about 18 m); the radio's display shows three decimals.

Verification: four messages with manually entered positions (N 0°00.00 E 0°00.00, N 0°00.01, N 54°14.95, W 0°23.42) decoded to exactly those positions, and every observed block, including five from a real fix, is rebuilt byte for byte from its decoded fields. A real fix of N 54°14.944 W 0°23.422, altitude 74 m on the radio's display, decoded as N 54°14.94 W 0°23.42, altitude 74 m. `ysfpos.py` has the decoder and encoder.

### 5.7 Position in voice transmissions

A voice transmission in voice/data mode 2 (FICH DT 2, FT 7) sends eight frames in a repeating cycle (FN 0 to 7). Each frame carries 10 data bytes: 200 coded bits taken as the first 40 bits of each of the five 144-bit channels, interleaved 5 wide, decoded with the same convolutional code, whitening and CRC-16 as 4.3 (80 data bits).

| FN | Content |
|---|---|
| 0 | `*****` + sender radio ID |
| 1 to 3 | sender callsign (three copies) |
| 4 | spaces |
| 5 | five spaces + sender radio ID |
| 6 | 4 bytes, then the first six bytes of the position block |
| 7 | the rest of the position block, `0x20`, `0x03`, checksum |

FN6 and FN7 joined give 20 bytes: a counter byte, three bytes (`22 62 5f` in the capture), then 13 bytes of the Mic-E block of 5.6 (the `3`, six latitude digits, three longitude bytes, three speed and course bytes), `0x20`, `0x03` and a checksum. The checksum is the sum of the first 19 bytes (the `0x03` included) modulo 256. There is no symbol and no altitude. The same cycle repeats for the whole transmission. A capture with GPS on decoded to N 54°14.94 W 0°23.43.

With GPS data transmit off the cycle is seven frames (FT 6, FN 0 to 6) and FN6 holds only `counter, 22 61 5f, 33, 03, checksum, 00 00 00`. The middle byte is `61` (`a`) without GPS and `62` (`b`) with it, the same step as `Ge_` and `Gf_` in the text record. The checksum rule is the same (sum of the bytes up to and including the `0x03`). FT therefore also tells the two cases apart: 6 without a position, 7 with one. A decoder that only looks at FN6 and FN7 of FT 7 cycles records nothing for a GPS-off radio.

Other voice modes (DT 0 and 3) and other radio models were not captured.

### 5.8 WIRES-X control frames

A radio in WIRES-X (X) mode sends its commands as data FR records with the same container as a text message: the 40-byte header, the radio ID at offset 55, a counter byte at 60, a 3-byte command at 61 to 63 (`5d xx 5f`, i.e. `]` + one command byte + `_`), a payload from 64, `0x03` and the checksum of 5.3. The record is as short as the command needs: FT = number of 40-byte frames minus 1, and the terminator frame's counter is `((frames + 1) << 1) | 1`. A text message sent from the same screen is an ordinary 200-byte record (`Ge_`) addressed to the room.

Commands seen (FT5D, a YSF reflector reached through a gateway; no reply was received, a reflector does not answer WIRES-X):

| Action on the radio | Command | Frames (FT) | Payload (from offset 64) |
|---|---|---|---|
| Category "Local News" selected | `5d 66 5f` (`]f_`) | 3 (2) | `3A1` |
| NEWS STATION selected | `5d 63 5f` (`]c_`) | 2 (1) | `3DNEWS17989` |
| download, message | `5d 6c 5f` (`]l_`) | 3 (2) | `3` `14561` `17989` `120` and spaces, then `0` at offset 83 |
| download, picture | `5d 6c 5f` (`]l_`) | 3 (2) | `3` `14561` `17989` `220` and spaces, then `0` at offset 83 |
| upload, message entered and sent | `47 65 5f` (`Ge_`) | 5 (4) | normal text record, destination ID `14561`, destination callsign `GB-CCARC` |

The destination of the message sent from the WIRES-X screen was the room's ID `14561` and its name `GB-CCARC` instead of blank and `**********`. The same `14561` appears in the download command. `17989` appears in both the NEWS STATION and download commands and is not yet explained, nor are `3A1`, the trailing `20` or the meaning of the command bytes. The digit after `17989` selects the download type: `1` message, `2` picture. The values come from only a few presses and a single room.

An FT3D sending download, message (through a hotspot) used the same command with the first payload character `0` instead of `3`, and its checksum sum starts at offset 13 instead of 22 (two requests, 15 s apart). Radio IDs are case sensitive and can contain lower case letters (`EAggJ`). The FT3D's ordinary text messages (a GPS-attached `Gf_` record to `**********`) use the same offset-13 checksum, so a receiver should accept a sum starting at either 22 or 13. The checksum rule held for all of them.

An FTM-400 (broadcast text with GPS attached, `Gf_`, 240 bytes) differs in two ways. The first byte of the position block at offset 64 is `%` (`0x25`) instead of `3`, and the voice position (section 6) carries the same `%`. The checksum is the sum of bytes 60 to the `0x03` inclusive, modulo 256, stored after the `0x03`. A receiver should accept the sum from 22, from 13 or from 60 (inclusive of `0x03`). The FTM-400 also sent a 2-frame record with command `]q_` (`%` payload) before the message, which is not decoded. One capture, one message.

### 5.9 Answering a News Station download with text messages

With the radio on the News Station screen (download, message) showing "Waiting", a directed text message (5.4: destination ID and callsign of the radio) sent to the reflector cleared the wait and opened the radio's message log (FT5D). Three directed messages sent one after another all arrived. No WIRES-X reply format was needed. The request is the `]l_` record of 5.8; the requester's radio ID is at offset 5 and 55 and its callsign at offset 10. An upload from the News Station screen is a single text record (`Ge_`) whose destination ID and callsign are the room's (5.8), with no other command. The picture download request (5.8) is the same `]l_` command with `2` in place of `1`; the voice request was not captured and probably uses `3`.

## 6. Decoding procedure

1. Check the sync word, decode the FICH, and confirm its CRC.
2. If `DT = 1`, split bits 240 to 959 into the two units (section 4.2).
3. Decode each unit (section 4.3). Discard the frame if either CRC fails.
4. Start a record at FI = 0. Take frames FN0 to FNn from the FI = 1 frames, first copy winning. End at FI = 2.
5. Join the 40-byte frame segments into the record.
6. Find the `0x03` end marker. The text is the 80 bytes before it. The 10 bytes before the text are the destination callsign, the 5 before that the destination radio ID.
7. Verify the checksum.

## 7. Generation procedure

1. Build the 200-byte record (section 5.2), including sequence number, current time and checksum.
2. Split it into five 40-byte segments, each as two 20-byte units.
3. Encode each unit (4.3), place the two units into a frame (4.2).
4. Prepend the sync word and the FICH. The FICH bits are most safely copied from a real transmission by the same radio: they depend only on FI, FN and FT.
5. Frame sequence and counters as in 5.1, packed as `YSFD` packets (section 3), sent about 100 ms apart after a `YSFP` login, then `YSFU`.

## 8. Reference implementation

Small Python 3 tools (standard library only) accompany this document:

| Tool | Purpose |
|---|---|
| `ysfcap.py` | Passive capture of `YSFD` frames from one callsign on a reflector, to a JSON lines file (needs root for a raw socket; never transmits). |
| `ysfdec.py` | Decodes frames (FICH, data units, record assembly, checksum, text and addressing). `--records` prints assembled records; `--selftest` runs an encode/decode round trip. |
| `ysfpos.py` | Decodes and builds the 19-byte GPS block (APRS Mic-E, section 5.6). |
| `ysfgps.py` | Lists the decoded position and raw block of every GPS-attached message in a capture, and compares them with positions you set. |
| `ysfdiff.py` | Shows which byte positions change with the message text across repeated captures. |
| `ysfreplay.py` | Feeds a capture through the `ysfmsgd.py` decoder and records the positions it holds, stamped with the capture time. |
| `ysfsend.py` | Builds and sends one text message, broadcast or (`--to-call`, `--to-id`) directed. `--check` compares its encoder with a real capture; `--dry FILE` writes the frames without sending; `--live` sends. |
| `ysfnews.py` | Service that answers News Station download requests (5.9) with the lines of a news file as directed text messages. |

Core primitives (from `ysfdec.py`):

```python
def crc16(bits):                     # x^16+x^12+x^5+1, init 0, inverted
    crc = 0
    for b in bits:
        fb = ((crc >> 15) & 1) ^ b
        crc = (crc << 1) & 0xFFFF
        if fb:
            crc ^= 0x1021
    return crc ^ 0xFFFF

def whitening(n):                    # PN(9,5)
    s = [1, 0, 0, 1, 0, 0, 1, 1, 1]  # S0..S8
    out = []
    for _ in range(n):
        out.append(s[0])
        s = s[1:] + [s[0] ^ s[4]]
    return out

def conv_encode(bits):               # rate 1/2, K=5, G1 then G2, 4 tail zeros
    hist = [0] * 5
    out = []
    for b in bits + [0, 0, 0, 0]:
        hist = [b] + hist[:4]
        out.append((hist[0] + hist[3] + hist[4]) & 1)
        out.append((hist[0] + hist[1] + hist[2] + hist[4]) & 1)
    return out

def interleave(dibits, width):       # write rows of `width`, read columns
    rows = len(dibits) // width
    return [dibits[r * width + c] for c in range(width) for r in range(rows)]
```

Test vector: `whitening(40)` packed into bytes is `93 d7 51 21 9c`.

## 9. Open questions

- **GPS-attached messages.** Decoding is done (5.6). Not yet tested: sending one to a receiving radio, the south and east/west flags beyond the cases above, longitudes of 10 degrees or more, and what the radio does with the symbol bytes and the message bits.
- **Meaning of fixed fields:** `*****`, the three callsign copies, `Ge_`/`Gf_`, the `3`, `0`, `00` markers, and the counter byte are reproduced exactly but not explained. The counter byte's wrap-around is not understood.
- **Other callsigns and radio IDs:** the checksum range and field layout were validated with one sender identity. A real receiver has not been tested with different identities or callsign lengths.
- **FICH fields** other than FI, FN, FT and DT, and their values for other message types.
- **WIRES-X:** only the requests from a radio were captured (5.8). Replies from a node, other commands, and the meaning of the payload fields are unknown.
- **Directed messages** were generated and received by an FT5D (5.9). Other models were not tested.
- **Other models and message modes** (images, data files, group messaging).

## 10. Responsible use

- Transmit only under your own callsign and licence conditions. The sender tool takes a callsign and radio ID that you supply; use your own.
- Text on a reflector is visible to everyone connected to it. If you display it, consider limiting it to broadcast messages and to a short time, and consider that others may not expect it to appear on a web page.
